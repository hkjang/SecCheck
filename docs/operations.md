# SecCheck 운영 가이드

## 구성

```text
사용자 / Keycloak
        │ HTTPS
Reverse Proxy (TLS, allowlist)
        │
SecCheck container ───── PostgreSQL
        │
encrypted evidence volume
```

Redis나 외부 CDN은 필요하지 않습니다. UI, 한글 PDF 글꼴, 기본 workbook과 migration이 이미지에 포함됩니다.

## 첫 구동

1. PostgreSQL DB와 전용 최소권한 계정을 생성합니다.
2. 네 환경변수만 구성하고 `seccheck:v<version>`을 시작합니다.
3. `/ready`가 200인지 확인하고 bootstrap 관리자로 로그인합니다.
4. 관리자 설정에서 Keycloak Issuer, Client ID, Client Secret, Callback URL을 입력한 뒤 Discovery Test를 실행합니다.
5. OIDC 관리자를 확인한 다음 필요하면 bootstrap 계정을 비활성화합니다.
6. TLS 환경에서는 Secure Cookie를 활성화합니다.

## 백업과 복구 훈련

- PostgreSQL: 일간 Full + PITR/WAL, 백업 자체 암호화
- `/app/data`: DB 복구 시점과 일치하는 증적 암호문 백업
- `ENCRYPTION_KEY`: 데이터와 별도 보관, 이중 통제
- 관리자 설정: DB 백업에 포함
- 복구 훈련: 격리 환경에서 실제 로그인, 목록, 증적 다운로드와 SHA-256, PDF/Excel Export까지 확인

복구 성공 여부만 기록하지 말고 백업 식별자, 목표/실제 RPO·RTO, 검증한 심의/증적 ID, 해시 결과, 수행자와 승인자를 기록합니다.

## 관측과 장애 대응

- `/health`: 프로세스 생존
- `/ready`: DB 연결 포함 준비 상태
- `/metrics`: Prometheus 지표 (아래 표가 전체 목록)
- 관리자 > 서버 로그: 요청 ID 기반 구조화 로그
- 관리자 > 감사로그: 주요 행위와 체인 검증

### `/metrics` 지표

인터넷이 닿지 않는 환경에서 경보 규칙을 직접 작성해야 하므로 전체 목록을 싣습니다. 모두 gauge이며 요청 시점에 계산됩니다.

| 지표 | 의미 | 경보 기준 예시 |
| --- | --- | --- |
| `seccheck_info` | 버전 정보 (`version` label, 값은 항상 1) | 배포 후 버전 확인용 |
| `seccheck_users_total` | 등록 사용자 수 | — |
| `seccheck_reviews_total` | 누적 심의 건수 | — |
| `seccheck_jobs_pending` | 대기 중인 작업 수 (재시도 대기 포함) | 단독 경보 부적합 — 아래 지표를 사용 |
| `seccheck_jobs_failed` | 5회 재시도 후 실패한 작업 수 | `> 0` 지속 시 조사 |
| `seccheck_jobs_oldest_pending_seconds` | 실행 시각이 지난 가장 오래된 작업의 대기 시간 | `> 900` 이면 워커 정지 의심 |
| `seccheck_http_requests_5m` | 최근 5분 API 요청 수 | — |
| `seccheck_http_errors_5m` | 최근 5분 5xx 응답 수 | 요청 대비 비율로 경보 |
| `seccheck_http_duration_ms_5m` | 최근 5분 평균 응답 시간(ms) | 평상시 대비 상승 |
| `seccheck_login_success_24h` | 24시간 로그인 성공 수 | — |
| `seccheck_login_failure_24h` | 24시간 로그인 실패 수 | 급증 시 자격 증명 공격 의심 |
| `seccheck_sessions_active` | 만료되지 않은 세션 수 | — |
| `seccheck_accounts_locked` | 잠긴 계정 수 | 급증 시 조사 |
| `seccheck_evidence_version_bytes` | 증적 암호문 총 용량(byte) | 볼륨 여유와 대조 |
| `seccheck_evidence_scan_pending` | 검사 대기 증적 수 | 감소하지 않으면 clamd 확인 |
| `seccheck_scan_failures` | `CLEAN`·`SKIPPED`이 아닌 증적 수 | `> 0` 지속 시 조사 |
| `seccheck_submission_failures_24h` | 24시간 제출 실패(4xx 이상) 수 | 급증 시 규칙·증적 정책 확인 |
| `seccheck_db_connections` | 커넥션 풀 상태 (`state` label: total/acquired/idle) | `acquired`가 `total`에 근접하면 포화 |

OIDC 장애 시 기존 세션은 만료까지 동작합니다. 비활성화된 bootstrap 계정을 사용할 필요가 있으면 이중 승인으로 일시 활성화하고, 사용 후 세션 종료·재비활성화 및 감사 이벤트를 확인합니다.

관리자 설정 > 알림에서 `테스트 메일 보내기`로 SMTP 경로를 먼저 확인할 수 있습니다. 일반 설정의 `서비스 주소`를 채우면 알림 메일에 해당 심의로 바로 가는 링크가 포함됩니다. 비워 두면 링크 없이 발송합니다.

사용자는 알림 화면의 `수신 설정`에서 유형별로 이메일을 끄거나, 즉시 수신 대신 하루 한 번 요약으로 바꿀 수 있습니다. 인앱 알림은 설정과 무관하게 항상 기록되므로 알림 이력이 사라지지 않습니다. 요약은 `notification.digest_hour`(기본 8시) 이후 사용자당 하루 한 번 발송됩니다.

이메일 알림은 SMTP Adapter와 PostgreSQL `FOR UPDATE SKIP LOCKED` 큐로 전송합니다. 최대 5회 지수형 재시도 후 `FAILED`가 되며 관리자 서버 로그와 `seccheck_jobs_failed` 지표에서 확인합니다. 인터넷이 없는 내부 SMTP 환경에서도 동작하며 가능한 경우 STARTTLS 또는 implicit TLS를 사용합니다.

## 계정 잠금과 로그인 보호

관리자 설정 > 접근 보안에서 조정합니다.

| 설정 | 기본값 | 설명 |
|---|---|---|
| `login_rate_limit_per_minute` | 30 | IP별 분당 로그인 **실패** 허용 횟수. 성공한 로그인은 계산하지 않습니다 |

성공한 로그인은 제한 대상이 아니므로, 여러 사용자가 하나의 NAT/Proxy IP를 공유하는 환경에서도 정상 로그인은 막히지 않습니다. 다만 그 환경에서는 실패 카운트도 함께 묶이므로 `trusted_proxies` 설정을 권장합니다.
| `max_login_failures` | 5 | 계정 잠금까지 허용할 연속 실패 횟수. 0이면 잠금 미사용 |
| `lockout_minutes` | 15 | 자동 잠금 유지 시간 |
| `idle_timeout_minutes` | 0 | 유휴 세션 만료. 0이면 세션 시간까지 유지 |

유휴 판정에는 화면에서 발생한 실제 요청만 반영되며, 읽지 않은 알림 배지의 1분 주기 폴링은 활동으로 계산하지 않습니다. 브라우저 탭을 열어둔 채 자리를 비워도 설정한 시간이 지나면 세션이 종료됩니다. 관리 설정은 저장 즉시 적용됩니다.
| `trusted_proxies` | (비어 있음) | X-Forwarded-For를 신뢰할 Reverse Proxy IP/CIDR |
| `require_totp_for_admins` | false | 관리자·검토자·승인자 계정에 일회용 코드 요구 |

Reverse Proxy 뒤에 배치하는 구성에서는 `trusted_proxies`를 반드시 설정합니다. 비워 두면 모든 요청이 Proxy 한 IP로 집계되어 분당 요청 제한과 로그인 시도 제한, 감사로그의 접속 IP가 조직 전체 단위로 묶입니다. 설정된 Proxy에서 온 요청만 X-Forwarded-For를 오른쪽에서 왼쪽으로 따라가며 실제 클라이언트를 판별하므로, 클라이언트가 헤더를 위조해 제한을 우회할 수 없습니다.

잠금은 `LOGIN_LOCKED` 감사 이벤트로 남고 `seccheck_accounts_locked` 지표로 관측합니다. 잠금 시간 경과를 기다리지 않으려면 관리자 > 사용자 및 역할에서 해제하거나 임시 비밀번호를 재발급하며, 두 작업 모두 감사로그에 기록됩니다. 로컬 계정 사용자는 개인 프로필에서 직접 비밀번호를 변경할 수 있습니다. 잠금은 신규 로그인만 차단하고 이미 열려 있는 세션은 종료하지 않으므로, 제3자가 잠금을 이용해 사용자를 강제 로그아웃시킬 수 없습니다.

## 2단계 인증 (TOTP)

로컬 계정은 개인 > 계정 보안 화면에서 RFC 6238 TOTP를 등록합니다. 서버는 외부 통신 없이 표준 알고리즘(SHA-1, 6자리, 30초)만 사용하므로 폐쇄망에서도 동작하며, 비밀키는 Master Key로 암호화되어 저장됩니다. QR 이미지 대신 비밀키와 `otpauth://` URI를 제공하므로 인증 앱의 수동 입력으로 등록합니다.

`require_totp_for_admins`를 켜면 대상 사용자는 다음 로그인 후 계정 보안 화면 외의 기능을 사용할 수 없습니다. 기기를 분실한 사용자는 관리자 > 사용자 및 역할에서 `코드 초기화`로 복구하며, 초기화 시 해당 계정의 모든 세션이 종료됩니다. 사용자는 같은 화면에서 자신의 활성 세션을 확인하고 개별 또는 일괄 종료할 수 있습니다.

## 증적 저장과 악성코드 검사

증적은 1MB 청크 단위 AES-256-GCM 스트림으로 저장됩니다. 청크마다 별도 nonce를 사용하고 추가 인증 데이터에 청크 순번과 마지막 청크 표시를 포함하므로, 잘리거나 순서가 바뀐 파일은 복호화 단계에서 실패합니다. 업로드·다운로드·ZIP 내보내기 모두 파일 전체를 메모리에 올리지 않습니다.

ClamAV 검사는 업로드 요청이 아니라 작업 큐에서 수행됩니다. 업로드 직후 증적은 `PENDING` 상태이며, `CLEAN`이 되기 전에는 다운로드, ZIP 내보내기, 심의 제출이 모두 거부됩니다. 악성코드가 탐지되면 증적이 논리 삭제되고 업로더에게 알림이 발송됩니다. 검사 대기 건수는 `seccheck_evidence_scan_pending`으로 관측하고, 5회 재시도 후에도 실패하면 증적이 `ERROR` 상태가 되어 관리자 개입이 필요함을 표시합니다.

## 검색 인덱스 (pg_trgm)

심의번호·서비스명·항목·증적 파일명·감사로그 검색은 부분 일치라 일반 인덱스로는 처리되지 않습니다. 마이그레이션 004가 `pg_trgm` 확장과 GIN 인덱스를 생성해 인덱스 스캔으로 전환합니다.

확장 생성 권한이 없는 최소권한 계정이라면 마이그레이션은 실패하지 않고 경고만 남긴 뒤 계속 진행하며, 검색은 순차 스캔으로 동작합니다. 데이터가 많다면 DBA에게 `CREATE EXTENSION pg_trgm;` 실행을 요청한 뒤 서비스를 재기동하면 인덱스가 생성됩니다.

## 스키마 마이그레이션

`internal/store/migrations/`의 번호 파일이 순서대로 각각 하나의 트랜잭션으로 적용되고, 적용된 버전은 `schema_migrations`에 기록됩니다. 기동 시 아직 적용되지 않은 파일만 실행되므로 재기동은 안전합니다. 현재 스키마 버전은 관리자 > 시스템 정보에서 확인합니다.

인덱스를 추가하는 마이그레이션은 해당 테이블에 쓰기 잠금을 잡습니다. 데이터가 많은 설치는 점검 시간에 배포하고, 배포 전 `CHANGELOG.md`에서 해당 버전의 스키마 변경 항목을 확인하십시오.

## 정기 보고

관리자 > 심의 리포트에서 기간별 처리 현황을 집계하고 Excel로 내려받습니다. 처리 기간은 최초 제출부터 최종 승인까지를 측정하므로 작성 중 대기 시간은 포함하지 않습니다. 진행 중 심의의 경과 기간 분포로 적체 여부를 판단하고, 반복 미흡 항목으로 다음 분기 교육·가이드 주제를 정할 수 있습니다.

## 시간대

일반 설정의 `표시 시간대`(IANA 이름, 예: `Asia/Seoul`)가 화면, Excel·PDF 내보내기, 알림 요약 메일 시각에 모두 적용됩니다. 컨테이너 자체는 UTC로 동작하며 시간대 데이터는 바이너리에 내장되어 있으므로 호스트 설정과 무관하게 동일하게 동작합니다. 값이 비어 있거나 알 수 없는 이름이면 UTC로 표시하며, 저장 시 유효성을 검증합니다.

**v0.6.0 이하에서 올라오는 경우 주의**: 일일 요약 발송 시각(`digest_hour`)이 지금까지 컨테이너의 UTC 기준으로 동작했습니다. `Asia/Seoul`을 설정하면 같은 값이 KST 기준으로 해석되므로 실제 발송이 9시간 앞당겨집니다.

## 작업 큐 운영

이메일 알림과 증적 악성코드 검사는 PostgreSQL 작업 큐에서 처리되고 5회까지 지수 백오프로 재시도됩니다. 관리자 > 작업 큐 화면에서 대기·실행·실패 건수와 마지막 오류를 확인하고, 개별 또는 실패 전체를 다시 큐에 넣을 수 있습니다. 검사 실패로 `ERROR` 상태가 된 증적은 재시도 시 `PENDING`으로 되돌아가 다시 검사됩니다.

SMTP나 clamd 장애가 복구된 뒤에는 `실패 N건 모두 재시도`를 한 번 눌러 밀린 작업을 처리하십시오. 재시도 행위도 감사로그에 남습니다.

## 감사 체인 검증

`체인 검증`은 마지막으로 검증에 성공한 지점 이후에 추가된 이벤트만 확인하므로, 이벤트가 수백만 건 쌓여도 일상 점검 시간이 늘어나지 않습니다. 검증 지점은 `audit_chain_state.verified_sequence`에 기록됩니다. 백업 복구 직후나 정기 감사처럼 전체를 다시 확인해야 할 때는 `전체 재검증`을 사용합니다.

검증에 실패하면 서버 로그에 ERROR로 남고 **모든 시스템 관리자에게 인앱 알림이 발송**됩니다. 검증을 실행한 사람만 알게 되는 상황을 피하기 위한 설계입니다. 이 경우 데이터베이스 직접 변경 여부를 즉시 확인하십시오.

## 증적 무결성 검증 (복구 훈련)

복구 훈련에서 데이터베이스 백업과 증적 볼륨이 같은 시점에 확보되었는지 실제로 증명할 수 있습니다.

```bash
docker compose exec seccheck /app/seccheck verify-evidence
docker compose exec seccheck /app/seccheck verify-evidence --sample 200   # 표본 검사
docker compose exec seccheck /app/seccheck verify-evidence --json         # 파이프라인용
```

모든 증적을 복호화해 파일 크기와 SHA-256을 DB 기록과 대조하고, 실패가 하나라도 있으면 종료 코드 1을 반환하므로 훈련 스크립트에서 그대로 실패 처리할 수 있습니다. 파일 누락, 키 불일치, 해시 불일치를 각각 구분해 보고합니다.

## 데이터 보존 자동 정리

서비스가 시작 1분 뒤부터 매시간 다음을 5,000행 단위로 정리합니다. 별도 cron이 필요하지 않습니다.

- 만료된 세션과 OIDC state
- `COMPLETED` 7일, `FAILED` 90일 경과 알림 Job
- 일반 설정 `retention_days`(기본 1825일)가 지난 서버 로그와 인앱 알림
- 잠금 시간이 지난 계정의 실패 카운터
- 논리 삭제 후 `upload.deleted_evidence_retention_days`(기본 90일)가 지난 증적의 **암호문 파일**

감사로그는 해시 체인 검증을 위해 자동 삭제하지 않습니다. 증적도 메타데이터 행(파일명, SHA-256, 삭제자, 삭제 시각)은 보존하고 암호문만 제거하므로, 삭제된 증적이 존재했다는 사실은 감사 시 그대로 확인할 수 있습니다. 정리 결과는 `maintenance` component 서버 로그에서 확인합니다.

`verify-evidence`는 데이터베이스에 대응 레코드가 없는 **고아 파일**도 함께 보고합니다. 고아 파일은 자동 삭제하지 않습니다. 볼륨에 예상치 못한 파일이 있다는 것은 운영자가 확인해야 할 사안이지 유지보수 작업이 조용히 지울 일이 아니기 때문입니다.

## 릴리즈 게이트

태그를 push하면 릴리즈 워크플로가 다음을 순서대로 확인합니다.

1. `VERSION` 파일과 태그 이름 일치
2. **해당 커밋의 security-ci 성공 여부.** CI가 아직 실행 중이면 최대 20분 기다리고, 실패했거나 CI 기록이 없으면 릴리즈를 중단합니다.
3. PostgreSQL 통합 테스트를 포함한 전체 테스트
4. 프런트엔드 빌드와 이미지 빌드
5. Trivy 컨테이너 취약점 게이트 (CRITICAL/HIGH)
6. 단일 자산 패키징과 provenance attestation

2번은 v0.20.0에서 CI가 실패했는데도 릴리즈가 성공한 뒤에 추가했습니다. 릴리즈 작업에는 데이터베이스가 없어 통합 테스트가 조용히 skip되었고, govulncheck·gitleaks·DAST 게이트도 릴리즈 경로에는 없었습니다.

## 업그레이드와 롤백

1. DB와 증적 볼륨을 함께 백업합니다.
2. 새 `seccheck:v<version>` image를 별도 검증 환경에서 시작합니다.
3. `/ready`, 로그인, 템플릿 Snapshot 불변성, 증적 다운로드를 확인합니다.
4. 운영 이미지만 교체합니다. migration은 시작 시 멱등 적용됩니다.
5. 애플리케이션 롤백 전에는 해당 버전이 이미 적용된 DB schema를 읽을 수 있는지 release note를 확인합니다.
